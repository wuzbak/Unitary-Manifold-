## B5 — Campaigns and Browsers: Play, Research, and Authority

Product 23, **PsiCat DM Guide & Player Assistant**, and Product 24, **PsiCat Web Browser**, have an obvious shared word in their names. Their common design problem is more interesting than the word: they make complex environments navigable while giving their users consequential controls. One environment is a role-playing campaign; the other is a browser and research workspace. In both, a good interface makes the next move easier to understand without pretending to make the decision on your behalf.

The DM Guide is an offline-first campaign assistant for Dungeons & Dragons 5e and 5.5e. Its README describes separate Dungeon Master and player dashboards, invite-code joins, character import, campaign tracking, encounter planning, XP, treasure, gold and item tracking, maps, NPCs, image pushes, and PsiCat guidance. The implementation separates models, compendium and rule data, assistant logic, server, and service layer. The user-facing flow begins with a locally launched service and campaign state, then routes requests through campaign or character operations. A DM’s campaign state and a player’s character view are distinct product roles; the assistant’s job is to support those activities, not to take ownership of the campaign.

This makes Product 23 a useful case study in state boundaries. A character import is not just prose pasted into a chat: the import has to be represented in the product’s data model. XP and gold changes should be treated as campaign state transitions, not as casually generated suggestions. Rules-aware coaching can help explain a mechanic, but the DM retains the authority to adjudicate a table’s rules and the players retain agency over their choices. The word “offline-first” describes an architectural posture, not an absolute privacy guarantee for every setup: a user should still inspect any configured assistant endpoint, network requests and data-storage behavior before entering sensitive campaign material.

A teaching workflow can start with a blank local campaign. The DM sets the campaign baseline and creates an NPC; a player imports a character and joins through the intended invite path; the table uses a planned encounter and records a reward. At each step, the group can inspect which data changed, who can see it, and whether the change is persistent. Then ask the assistant a rules question and compare the answer with the cited rulebook or the DM’s chosen rules source. This test makes the difference between state mutation and explanation concrete. A campaign tool that proposes a treasure award and a campaign tool that records it are not doing the same thing.

Product 24, **PsiCat Web Browser**, is a Chromium-based browser foundation spanning Electron desktop, Android native-tab structure, a browser extension, research sidebar, local sync backend scaffold, Playwright-first browser proving ground, notebook, sync packet workflows, and import/export. These are components at different maturity levels, not a guarantee of feature parity across operating systems. The README explicitly labels the project a foundation and gives a separate honesty boundary. A reader should therefore ask of each workflow whether it is implemented, scaffolding, or a proposed integration—not infer production readiness from a platform directory.

On desktop, the application’s central concern is not only rendering a web page; it is controlling boundaries between page content, privileged Electron processes, the PsiCat sidebar, local services, and any sync mechanism. The browser’s tests probe page context, IPC, startup diagnostics, lifecycle, sidecar behavior, browser core and Product 20 client behavior. Such tests can establish that the specific tested contract behaves as intended in the test setup. They do not prove that every website is safe, that all IPC paths are secure under every threat model, or that a local sync scaffold is a production synchronization service.

The sidebar’s research flow is a particularly useful integration example. A user can select or summarize a page, provide context to PsiCat, receive a response, and preserve a notebook or sync packet. The page content should be treated as untrusted input. A quoted instruction within a webpage is not automatically an instruction from the user or system. The correct product design is to make the source, transformation and destination of selected content visible, and to require explicit permission before meaningful transfer. A copied page snippet, a locally stored note, and a remote provider request are three different data-flow events.

### A joint research exercise

Use the browser to inspect a public rules reference for a hypothetical campaign question. Do not copy the entire page by default. Select the smallest relevant excerpt, include its URL and a note about the edition, then ask PsiCat for a summary. Compare the output to the source rather than relying on a paraphrase. If the result is useful, save a note that distinguishes the source text from the assistant’s explanation. Then return to the DM Guide and decide whether any campaign change should follow. The assistant does not get to transfer “the answer” into character state unless the user performs the explicit campaign action.

The same sequence works for a scientific paper. Start with a public article in Product 24. Record its bibliographic identity and whether it is an original study, review, preprint or commentary. Ask PsiCat to extract a claim, but preserve the exact passage and page or section citation. Then check the analysis in the paper. Do not let a browser sidebar’s confident prose collapse publication metadata, a measurement, and the repository’s interpretation into one sentence. If the article is from outside the UM corpus, label it external literature. If the product lacks remote sync or a tested connector for the use case, keep notes local rather than improvising an undocumented integration.

Product 24’s operational vocabulary should be deliberately modest. “Browser foundation,” “Android shell,” “sync backend scaffold,” and “Playwright proving ground” are more informative than a blanket statement that the product is a finished secure browser. The file tree includes Electron `main`, `preload`, and runtime code; Android structure; extension code; sync backend; tests; and a workbench bridge. Each surface has its own lifecycle, permission model and failure modes. If desktop IPC is blocked, the web page may still render while privileged features fail. If local service discovery fails, the sidebar can lose a capability without the browser itself being down. Good diagnostics distinguish those states.

A safe and useful browser workflow follows a simple sequence: define the research question; choose the source; select minimal context; review the destination; perform the assistant query; inspect citations; save a provenance-bearing note; and separately approve any stateful action. This separates browsing from retrieval, retrieval from interpretation, and interpretation from action. It also makes failures visible. A model timeout is not an empty search result; a blocked local bridge is not proof that the page contains no relevant information. The user should be able to continue manual research without mistaking a failed AI call for a negative result.

The two products also show why one “AI” label hides several distinct capabilities. The DM Guide may call a remote or local assistant path for rules-aware prose while keeping campaign state in its own service. Product 24 can supply page context to Product 20 while the browser renderer and extension have separate controls. Product 20 can retrieve local evidence without calling a model. Even in one screen, the source of each output can differ. The best UI names these systems and their boundary. In book prose I do likewise: this passage explains documented behavior; it is not an assertion that I queried the active campaign server or browser.

## B6 — A Braided Brain, an Evidence Runner, and a Workbench

Three products offer three different meanings of “learning.” Product 25, **PsiCat Braided Brain**, teaches through a puzzle. Product 26, **UM-ARTS**, supervises and records tests. Product 27, **PsiCat's Vite Web Workbench**, scaffolds and previews frontend projects. A player may learn a concept; a test suite may verify a behavior; a developer may build a page. None of those by itself demonstrates that a model has learned, that science has been validated, or that arbitrary code is safe.

Product 25 is a responsive, installable browser game. The player moves PsiCat through wrapped toroidal boards, solves missions, stabilizes gut-brain or fly-brain lanes, braids PsiCat with PhiCat, and unlocks entries in a science atlas. The app’s core game logic is in `ui/game-core.js`; `app.js` connects rendering, controls, offline support, optional coaching and export. It preserves progress locally by default. A user can deliberately export a save bundle or a training packet, and the packet captures task-derived records such as mission outcomes, mastery, concept selections and lightweight puzzle traces. It does not secretly collect biometrics or profile the player.

The teaching value is in the game loop: face a concrete constraint, try a route, observe the result, and connect the puzzle mechanic to an explicitly labeled science card. The atlas distinguishes established findings, bounded empirical summaries, educational analogies and product behavior, while exposing scope and unvalidated correspondences. The game’s toroidal topology can help someone reason about wraparound movement; it does not demonstrate that a biological brain literally has the game’s topology or that the repository’s geometric correspondences have been proven. The game’s neuroscience inspiration includes public connectome references and repository material, but the authors explicitly disclaim proof of a consciousness theory.

The optional Product 20 coach can answer a player’s question; a local fallback prompt remains when the coaching endpoint is unavailable. That optional branch matters: playing the core puzzle does not require the remote coaching path. The local browser-storage model and explicit export mean data does not leave the device unless the player chooses to export it or deliberately points the coach at a local Product 20 endpoint. A downloaded training packet is a record, not a training run. It does not update model weights, establish competence beyond the recorded task, or prove that later answers improve.

For teaching, ask a learner to finish a mission and explain why a selected science-atlas card is labeled “analogy” rather than “established result.” Then export a packet and inspect the fields. Have the learner decide whether any field reveals more personal information than necessary. Finally, compare the actual gameplay trace with the player’s written explanation. This exercise examines the pedagogical tool and its evidence. It does not validate the physiology behind the analogy.

Product 26, **UM-ARTS**, is an evidence-first regression application. Its name expands to Unitary Manifold Audit, Regression, and Test Supervision. It discovers inventory, plans a selected execution, runs tests under a bounded configuration, captures structured receipts, evaluates them, supports compatible resume and artifact import, and provides bounded assistance. Its purpose is auditability—not scientific promotion. The engine creates a plan, then a distinct attempt; tests are assigned into jobs, invoked through a controlled process runner, and evaluated against structured receipts rather than terminal text alone. Artifacts and evidence receive hashes and seals; resume reuses validated successes into a new attempt rather than rewriting the old one.

The capture path has a separate role. Given a completed CI invocation and structured pytest receipts, capture evaluates that evidence without rerunning the tests. This distinction prevents a common reporting mistake: claiming that “capture passed the suite” when capture actually assessed an already executed suite. A captured artifact is not a new experiment; it is an evaluation of prior execution evidence. Reports also include selection and collection boundaries, execution result, process details and errors. If receipts are incomplete or inconsistent, evaluation can fail closed rather than treating console output as a substitute.

UM-ARTS also includes inventory and analysis functions that are intentionally bounded. Inventory walks the chosen repository scope and accounts for excluded paths. A code index can summarize structural facts about Python code. A context-assistance feature limits the paths it will read; it is not an unrestricted repository oracle. Lean capture records typed build or inspection evidence with explicit `proof_claim: false` and unresolved correspondence semantics where relevant. These details matter: a successful build or test run verifies an artifact within the declared scope, not the physical truth of a theorem or the empirical validity of a model.

The operator should define root, suites, selection, worker count and timeout before planning. After a run, inspect the manifest, job receipts, test identities and process-level evidence. A failed job stays failed; a partial attempt should not be renamed “complete.” Resume should produce a new attempt with compatible prior results, preserving the original. A report that says “passed” must name what was selected, what was excluded or deselected, whether collection succeeded, and whether there were internal errors. A suite-wide green label without that context is a lossy compression.

Product 27, **PsiCat's Vite Web Workbench**, scaffolds small frontend projects from reviewed Vanilla JavaScript and TypeScript templates, inspects bounded file lists, starts and stops Vite previews on loopback, and builds static output with a machine-readable receipt. A local dashboard and HTTP API use a bearer token. Native Product 20 tools are available when explicitly configured; write actions require an explicit `human_gate_approved: true` acknowledgement. The tool does not accept a token as a tool argument and does not return the token in receipts. It can therefore support governed tasks without turning every page into an open-ended agent execution surface.

The guardrails are concrete and must not be exaggerated. It binds to loopback; validates same-origin requests; requires a sufficiently long token for mutating API routes; constrains names, project count and source size; rejects symlinks; and loads no project Vite configs, PostCSS plugins, package scripts or arbitrary package managers. It scaffolds only reviewed templates, runs selected Vite actions, and does not execute arbitrary shell commands. But it is explicitly **not an OS sandbox**: project source runs in the browser, and Vite transforms it. Use trusted code and do not expose the local service to a network. Preview is not a production server; static output still needs independent review before deployment. Vite’s build strips TypeScript syntax but does not type-check it—an important example of a tool name being narrower than a user might assume.

### The evidence chain across all three

These products occupy distinct stages of a healthy research and development cycle:

- The game creates an optional, task-bounded learning record.
- UM-ARTS executes a declared test scope and captures structured evidence.
- The Workbench creates or previews an artifact through a narrow, local tool contract.

They can connect, but they should not collapse into one claim. A training packet from a game is not a test receipt. A test receipt is not a deployment authorization. A Vite build receipt is not a security review. A passing test that covers a workbench endpoint does not prove that every user-created project is safe. If future orchestration sends a packet from one product to another, preserve provenance and semantics: say “game export,” “test execution,” or “build result,” not merely “evidence.”

Consider a small teaching project: create a frontend visualization of a synthetic puzzle result. Start with Product 25’s explicitly exported practice bundle, not hidden browsing state. Inspect the bundle and remove any irrelevant information. Use Product 27 to scaffold a reviewed template, inspect its bounded file list, and ask Product 20 for an explanation only if the optional bridge is configured. Require approval before creation, preview and build. Run the relevant tests under UM-ARTS or the product’s own test suite with a named scope. Save each receipt. The final artifact can say “a static demo generated from a synthetic game record and built locally.” It cannot say “an experimentally validated model of cognition.”

The workflow demonstrates teaching, building, and checking in one chain without converting their different meanings into a single AI success score. If the Vite preview displays malicious or simply untrusted code, loopback and token controls are not a guarantee against browser-side behavior. If a Product 20 call fails, fall back to reading the code or docs rather than guessing that a scaffold action completed. If UM-ARTS reports an incomplete receipt, stop and inspect before promoting the result. A clean user experience should not smooth over these states.

## B7 — Three Laboratory Consoles, Three Different Claims

Product 28, **AZ Calorimetry Console**; Product 29, **AZ Polariton Vortex Analyzer**; and Product 30, **AZ Materials Screening Engine** are applied-science software. They help structure a measurement or compute a model-derived quantity. They are not external laboratories. No apparatus enters a run-sheet by magic, and no experimental provenance becomes authentic merely because a SHA-256 digest has been calculated. The most useful way to learn these products is to follow exactly what enters each one, what transformation is performed, what exits, and what the output cannot establish.

Product 28’s first path is a run-sheet generator. It reads a D/Pd loading resonance target `x=7/8=0.875` from the repository’s lattice-dynamics module and pairs it with the F1 calorimetry gate from the falsification protocol, then emits a temperature-ramp schedule and monotonic loading-ratio curve. This is a proposed schedule artifact: it does not drive a reactor or measure a sample. Its second path is the live COP tracker. The tracker consumes `(power_in, power_out)` samples and uses the repository’s `cop()` and `is_excess_heat()` functions to report one of `AWAITING_DATA`, `NO_EXCESS_HEAT`, or `EXCESS_HEAT_OBSERVED`, under the project’s COP > 1.01 threshold. A UI result can therefore mean only that the supplied pair produced the corresponding code outcome.

The third Product 28 path is the strict measurement importer. It accepts a CSV with exact ordered headers `timestamp_s,power_in_w,power_out_w`, at least two samples, and acquisition metadata declaring run, instrument, calibration, acquisition time, source reference and units. It validates finite increasing timestamps and finite, physically permitted wattages, rejects malformed or incomplete batches as a whole, retains hashes of the exact source bytes and accepted line-numbered samples, then emits an artifact. Its trapezoidal energy integration applies only over the recorded interval; it does not extrapolate. For irregularly sampled, changing power, the integrated-energy COP differs from the tracker’s arithmetic sample-mean COP. The software marks this distinction. Gaps assume linear power evolution and require operator review.

The importer’s `ABOVE_THRESHOLD` or `NOT_ABOVE_THRESHOLD` is a format-and-threshold screen, not proof of excess heat. It does not do uncertainty propagation, baseline subtraction, control analysis, sensor-to-power conversion, or independent calibration. Calibration identifiers are operator declarations, not checked certificates. Hashes establish byte identity, not who produced the bytes. A well-formed file can be a fictional file. The phase boundary is unambiguous: Product 28 is Phase 0 instrumentation software; a procedure, real external lab run, and reporting into `FALLIBILITY.md` are distinct future work. The underlying vertex connection from radion scale to lattice scale is also documented as not yet computed.

A responsible workflow uses actual calibrated power measurements from an instrument export, keeps the original files, records the calibration source and lab notebook reference, imports the measurements, and reviews the strict output alongside controls and uncertainty analysis done elsewhere. Do not substitute thermocouple voltages for power or let the importer infer conversion. Do not treat the example run-sheet as an experimentally tested protocol. A status page or run sheet is software evidence, not calorimetry evidence.

Product 29 analyzes already-tracked feature positions exported from pump-probe measurements. Its schema has `position_um`, `timestamp_fs`, and `half_angle_deg`; it expects a dataset/source declaration and validates exact schema, units, numeric ranges and grouping by exact half-angle. Each angle must have at least two distinct timestamps describing one tracked trajectory in a consistent calibrated coordinate system. It does not accept raw images or intensities and does not perform feature tracking. It fits position against time independently at each half-angle using ordinary least squares and every sample, converts the signed velocity to `v/c` using `c=0.299792458 μm/fs`, and compares the resulting curve with the repository’s polariton-vortex prediction, using `c_s=12/37` by default.

The report includes dataset ID, declared source, input-byte hash, timestamp, frame counts, fit residuals, predicted values, measured-minus-predicted residuals and crossing information. But fit RMSE describes departure from a constant-velocity line, not calibrated measurement uncertainty. A two-point fit cannot assess fit quality and triggers a warning. A sampled or interpolated `v/c=1` crossing is not an uncertainty interval or a fitted critical angle; no extrapolation is performed. Multiple crossings are retained and labeled. Negative slopes remain negative. Missing or invalid input yields an explicit failure, not a synthetic report.

The distinction between two Product 29 modes is pedagogically important. A no-argument CLI can produce a prediction-only summary; the explicit `/api/demo-comparison` route generates synthetic values from the prediction itself. That is a self-consistency exercise, not evidence. The `/api/analyze` endpoint accepts a measurement contract; it returns errors for invalid schema or body, wrong method, unsupported type or unknown route. The local UI uploads JSON and analyzes it in memory without saving the uploaded file. Keep the service on loopback; it is not authenticated or a public production service. An accepted file is still not authenticated as an experiment; the declared source and calibration metadata can be false or mistaken.

Product 30 consolidates critical-angle, Fröhlich-polaron and metamaterial formulas into a parameter-agnostic `MaterialCandidate` function. Inputs include dimensionless coupling α, LO phonon energy in meV, band mass in electron-mass units, relative permittivity and optionally relative permeability. Outputs include polaron binding energy, effective-mass ratio, polaron radius, metamaterial flags and the framework’s fixed critical half-angle. `rank_candidates()` sorts by absolute divergence of supplied α from the repository’s canonical `froehlich_alpha_um(5,5,7)` value. That is a descriptive ordering rule, not a performance metric or proof of the best material.

The real-record path accepts CSV or JSON with source, source record ID and conditions. Source and ID must be nonempty and unique as a pair; conditions should identify phase, composition, temperature, frequency, orientation and method as relevant. The input file is size- and row-bounded. Values must be finite and positive where required; missing optional `mu_r` assumes `1.0` and the output records that assumption. Invalid columns, duplicate keys, ragged rows, unit errors, nonrepresentable outputs and invalid records fail the entire batch. There is no partial result, inferred property, unit conversion, remote Materials Project query, or demo fallback when the `screen` command receives bad input. Hashes identify the exact bytes but do not verify source authenticity or experimental context.

Product 30’s no-argument CLI and `/api/demo-rank` expose three illustrative placeholders; these must never be confused with material measurements. The actual `screen` command is the evidence-bearing path for supplied records, but “evidence-bearing” means provenance fields accompany the input—it does not mean the properties have been independently measured. Formula consolidation is Phase 0/1; a validated database comparison and real database inversion remain outside current scope. There is no fit, uncertainty propagation or scientific validation against measured materials yet. A screen can tell you what follows if supplied parameters are accurate and applicable. It cannot establish that they are.

### A worked laboratory progression

Imagine a group with a pump-probe dataset and candidate compound list, considering whether to pursue a cold-fusion experiment. First, Product 30 can screen candidate properties if the group has records with units, sources and conditions; those rankings are descriptive, and data provenance needs independent review. Product 29 can analyze manually tracked feature positions if there is an appropriate optical dataset; its assumptions about track identity, calibration and units must be checked before interpreting residuals. Product 28 can prepare a loading schedule and import calibrated power measurements once an actual calorimetry run exists.

The products do not form an automatic experimental chain in which a favorable materials score initiates a bench run and the bench run validates theory. An experiment plan needs human design, safety review, calibration and controls. A measurement needs authentic records and uncertainty analysis. A code-level result needs versioned inputs and outputs. A scientific claim needs interpretation, replication and scrutiny. The instruments can keep their local steps more legible; they cannot replace any missing step.

When an output is surprising, preserve the original inputs and ask focused questions. Did validation silently convert units? (These products try to avoid that.) Was a row dropped? (The importer rejects whole batches.) Did interpolation extrapolate? (The analyzer explicitly avoids extrapolation.) Did a demo value enter the real data path? (Strict APIs should not use fallbacks.) Did a hash prove the source? (No; it proves only identity of bytes.) Did a screen establish experimental relevance? (No; model applicability remains a human and scientific question.) These checks prevent a modest computation from becoming an extraordinary claim by accidental narrative inflation.

Finally, there is a difference between a software test and a laboratory protocol. Product tests can pass with fixture CSVs or constructed tracks. They show that a parser rejects malformed input, that the formula function returns expected outputs, or that an API emits the documented response. They do not show that an instrument was calibrated, an apparatus was built, a signal was independently measured, or a reported result replicates. The lab remains in the loop; the loop is not a metaphor.

## B8 — One Spine, Many Honest Instruments

The products in these two parts do not need to be forced into one monolithic application to work coherently. What they need is a shared language for identity, evidence, status, scope and promotion. That is the purpose of the repository’s **execution-spine convergence charter** and the **PsiCat ecosystem integration master plan**. The plans describe engineering convergence; they do not declare that every planned integration is complete.

The charter begins with a sober diagnosis: the repository has multiple active execution, artifact, readiness and status surfaces. Its thesis is one canonical truth/status spine, one governed execution spine, one canonical PsiCat control plane, one adjacent quantum execution lane, and a disciplined compatibility story. It names nine canonical truth surfaces—including `STATUS.md`, `FALLIBILITY.md`, `docs/CLAIM_MASTER_BOARD.md`, `docs/GATEKEEPER_SUMMARY.md`, `docs/TRUTH_LAYER.md` and the live-status JSON—that must stay synchronized when status-bearing work occurs. The command constraints are execution-first, truth-first, geometry-first, swarm-safe and branch-aware.

The shared contract calls for each emitted artifact or readiness packet to carry surface identity and kind; lane; current status; summary; canonical paths and sources; fail-closed governance metadata; compatibility metadata; health checks; and promotion metadata. The rule is powerful because different applications can remain different while their evidence becomes comparable. A test runner, a browser build, a science observation router, and an applied measurement importer do not need identical payloads; they need enough common structure to say where a record came from, which boundary it belongs to, whether required checks succeeded, and what action is permitted next.

The plan’s sequence is deliberately staged: establish boundaries; standardize artifact, health, routing/preflight and promotion metadata; keep `/api/psicat` the primary governed control plane while `/api/merlin` and `/api/ox` remain compatibility routes; attach adjacent quantum artifacts without hiding optional-backend status; move consumers toward common readiness surfaces; validate with tests, benchmarks and blocker reporting; then bind geometry-first execution and swarm-safe observability. This is not a license to skip the phases. “Target” does not mean “finished,” and a compatibility endpoint that still responds is not a competing canonical control plane.

The master integration plan adds a concrete architecture for coordinating the Base44 prototype and monorepo. Its own scope disclaimer says that this is an adjacent software track, not physics closure, intelligence certification, release approval or deployment proof. That line should remain visible whenever an integration diagram begins to resemble a product announcement. The plan’s center is accountable context, scoped memory, governed actions, reproducible evidence and honest boundaries. It treats PsiCat as a control surface connecting tools and artifacts, not as a magical model whose answer replaces independent evidence.

Think of the architecture as a transit system. Products 16–30 are stations with different tasks: synthesizing, drawing, teaching, routing, navigating, monitoring, defending, playing, browsing, testing, building or analyzing. Product 20 is a control plane and contextual navigator. The execution spine is the shared timetable and ticket format. A common ticket does not make a train, ferry and lab cart the same vehicle. It does let a reviewer know the origin, destination, status, permitted route and whether the bridge is out. Compatibility routes are old station entrances that remain usable but should not become the destination for new system design.

### An integration scenario, without imaginary wiring

Suppose a materials researcher wants to explore a polariton-vortex comparison. Product 30 screens actual property records, if supplied; Product 29 analyzes tracked pump-probe positions; Product 18 can orient a student to relevant repository writings; Product 20 can retrieve candidate source context; UM-ARTS can run a specifically declared regression suite; Product 27 can create a locally reviewed frontend for plotting a result. In an integrated future, a shared packet could identify each artifact’s source, status, lane, assumptions, health checks and compatibility caveats, all linked to the canonical truth surfaces.

But the existence of this coherent scenario does not prove that those products currently pass packets to each other automatically. Unless a corresponding adapter, test and runtime configuration demonstrate it, this is a design sketch. Today, each tool can be used deliberately and its output reviewed; that is enough to teach the workflow without claiming automation that has not been built. A responsible report would identify the handoffs as manual where they are manual and name any missing adapter as a blocker.

The scenario then grows a proper evidence chain. A materials-screen report should identify the input file hash, record count, source IDs, conditions and formula version. A polariton report should identify its dataset, source declaration, input hash, track assumptions, fit diagnostics and explicit non-validation disclaimer. A Reader note should identify the document version and the distinction between summary and source. A Product 20 retrieval result should retain query, selected context and ranking mode where the operational interface supports it. A UM-ARTS report should name the tested scope, collection and execution receipts, errors and excluded tests. A Workbench build should name the project and build receipt. Those facts let a human see both what happened and what remains unknown.

Now imagine the material batch is malformed. The correct flow is to stop the batch and report the input failure, not to substitute demo candidates. Imagine the polariton API reports an invalid unit or wrong content type. It should return an explicit error, not a favorable synthetic curve. Suppose UM-ARTS cannot validate a resume receipt. It should fail closed rather than assume the previous job passed. Suppose the Workbench’s local token is missing. It should refuse the mutating request. Suppose Product 20 retrieval returns unrelated pillars. The answer should say retrieval was weak and switch to direct source inspection. These are not embarrassing exceptions; they are the moments when architecture proves its honesty.

The charter’s sanity rules follow naturally: do not create a competing source of truth; do not create a local status ledger where a canonical one already exists; do not orchestrate without the shared contract; do not promote without receipt-backed benchmark evidence; do not imply an optional backend is guaranteed; do not upgrade physics as a side effect of infrastructure; do not make a legacy route the center; and do not permit hidden external automation or third-party commandeering. A discipline like this is not anti-ambition. It makes ambition cumulative rather than theatrical.

### Who decides what “ready” means?

Readiness should be decomposed. A component can be code-complete but unvalidated against real data. A local service can pass tests but not be deployed. A science hypothesis can be internally derived but lack empirical confirmation. A product can have an interactive demo while not being safe for public hosting. A successful CI capture can describe prior execution, while a test plan describes a different scope. Put these dimensions into separate fields and let the evidence answer each one. Avoid compressing them into one green badge.

This is also the right place to speak about the repository’s physics boundary. The canonical framework describes 208 hardgate physics pillars, but “hardgate” means the repository’s internal governance gate. It does not certify external empirical truth. Adjacent software and research products are not new hardgate claims by implication. A test count demonstrates repository regression status for a defined run, not the correctness of every physical proposition. The truth layer and fallibility documents preserve open problems, tensions and conditions; current truth sources outrank stale copied product text. When a product README carries a historical version or older claim, cite it as product documentation and check present status separately.

The integration work also needs a human responsibility model. A tool can classify, sort, display, parse, retrieve and report. People decide whether the result applies, whether the source is trustworthy, whether the operation is authorized, whether a scientific interpretation is warranted, and whether a deployment is ready. Some decisions should have explicit approval gates because they mutate state or create external exposure. Others require expert review because the software’s numerical output does not cover calibration or model validity. A “human in the loop” is not a ceremonial click; it is a named person with context, authority and an opportunity to reject or investigate.

### A compact review protocol for readers

When encountering any of Products 16–30, ask these questions in order:

1. **What enters?** Identify user-entered values, source files, live feed records, browser context, optional model calls, defaults and required metadata.
2. **What transforms it?** Name the parser, formula, ranking rule, threshold, model call, renderer or test runner. Distinguish default from optional paths.
3. **What exits?** Classify the result as a drawing, score, search hit, verdict, report, saved state, action or receipt.
4. **What can fail?** Look for rejected schema, missing source, timeout, empty retrieval, invalid unit, stale feed, blocked tool, partial test run or unsupported environment.
5. **What is verified?** State the exact scope of tests, fixture coverage, data provenance, calibration, benchmark or external replication.
6. **What does it not prove?** Name the scientific, operational, privacy, security or deployment boundary.
7. **What is the next authorized step?** Keep review, approval, promotion and publication separate.

If a product’s documentation does not answer one of these questions, mark the gap. A gap does not mean the product is useless; it tells the operator where independent judgment must enter. Do not infer safety from a product name, a high test count, a TRL number, or a passing demo. Read actual implementation, test contracts, deployment statements and evidence receipts. Do not infer active code from a catalog description alone. The code and the receipt are part of the argument.

The best possible outcome of these fifteen tools is not that every question receives a confident answer. It is that a reader can move from curiosity to a testable, traceable next step without losing sight of uncertainty. A Reader can bring someone to a source. An Observatory can reveal exactly how a declared rule classifies a supplied number. A monitor can place a feed record on a globe. A security engine can record a bounded analysis. A game can invite explanation. An audit runner can show what tests actually ran. A lab console can preserve measurements and assumptions. PsiCat can help navigate and explain. Each capability becomes more credible when it refuses to impersonate the others.

The spine we want is therefore not a conveyor belt that turns every output into certainty. It is a ledger of bounded transitions: source to context, context to computation, computation to report, report to human interpretation, and interpretation to an approved next action. At each junction, provenance travels with the record. At each failure, the state stays visible. At each promotion, the evidence is named. We do not need every instrument to speak in one voice; we need every voice to say what it knows and how it knows it.

That is the practical meaning of a governed ecosystem. It is not a promise that software will never err, that a model will never hallucinate, or that a scientific theory is confirmed. It is a design commitment to make error discoverable, uncertainty expressible, and action accountable. The cat can wander between rooms, but it does not get to redraw the floor plan while no one is looking.
