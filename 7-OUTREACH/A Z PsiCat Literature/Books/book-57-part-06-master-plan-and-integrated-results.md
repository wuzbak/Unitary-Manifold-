## C9 — Pin the map before calling it a result

There are two maps on the table. One is the repository’s broader PsiCat ecosystem integration plan, which asks how existing products can cooperate while preserving their owners, evidence, and human authority. The other is a more focused AxiomZero machine-learning capability program: twenty-one ambitions with a common architecture, dependency register, execution board, and measured implementation tranches. The second map extends the first; it does not replace it.

The broader integration master plan places Product 20 as the existing PsiCat control plane, Product 42 as capability discovery, Product 26 UM-ARTS as evidence and regression accounting, Product 24 as a browser host, and Product 44 as a way to compose evidence, memory, computation, and governed tools. It explicitly rejects an extra orchestrator, automatic authority, or the assumption that merely assembling several tools produces intelligence. Its staged integration work includes local context transport, capability/authority crosswalks, a browser roundtrip, memory quarantine, dependency-aware orchestration, bounded HDC and geometry experiments, measured kernel comparisons, and supervised release. That plan spans the ecosystem.

The ML capability program, in contrast, groups model execution, retrieval and agent memory, governed data assets, evaluation, monitoring, and rollback around an existing execution spine. It is an engineering plan within that larger boundary. It names Products 20, 21, 40, 43, 44, and 45 among its intended consumers or adapters, and it treats UM-ARTS and the execution spine as evidence/accounting foundations. It does not authorize Product 20 to become a new universal scheduler, nor does it introduce a second status ledger with authority to promote production. A JSON register tracks planned program deliverables; a board records the handoff; neither is a release authority.

## C10 — One execution spine, two model lanes

The ML architecture is a useful refusal. It refuses to solve integration by inserting a new controller between every product and every decision. The architecture diagram in the branch master plan starts with the existing portfolio—PC Suite, Browser, Journalist, scientific and domain products—then puts the PsiCat control plane over the existing execution spine. Beneath that, it brings together agents/retrieval, model execution, and governed data assets, with evaluation, monitoring, and rollback across them.

The canonical constraints are named in `9-INFRASTRUCTURE/EXECUTION_SPINE_CONVERGENCE_CHARTER.md`, and the plan directs re-use of `src/infrastructure/execution_spine.py` rather than a parallel orchestration scheme. Changes to the spine should be minimal and contract-driven. The program register is expressly not an automatic scheduler and does not confer action authority. A `next` command may identify dependency-ready planning candidates; it does not approve their execution. An execution board authorizes bounded packages, and people remain accountable for decisions with consequential effects.

This architecture is more than tidy diagrams. If the same system owns a model, approves its use, evaluates its quality, and announces its promotion, one convenient status can obscure several distinct judgments. Keeping a control plane for policy and approvals, an execution spine for receipts and promotion metadata, and capability packages for their own implementations helps retain those distinctions. It does not make the implementation trustworthy by decree; it gives reviewers identifiable places to challenge each claim.

The plan explicitly separates two model lanes:

* **Research lane:** Product 43’s NumPy toroidal transformer. Its architectural hypotheses are explored against conventional mechanisms under matched resources.
* **Applications lane:** pinned, supported pretrained backends that deliver practical language features through governed execution.

The lanes may share artifact, evaluation, and execution contracts. They are not substitutes for one another. A research transformer is not presumed to have application-grade language ability, and an application model’s practical utility does not settle whether a novel architecture adds value. Nor does an integration receipt prove a model is intelligent, safe, fast, aligned, or physically superior. The branch states that no physics-derived speed, alignment, or reasoning advantage is assumed.

This distinction helps explain how integrated work could nevertheless yield novel results. Novelty could emerge from implementing an algorithm rather than merely wrapping an existing library; from an end-to-end contract that makes model, tokenizer, corpus, features, lineage, and evaluation identities comparable; from a cross-product workload that can replay the same inputs through different backends; or from a negative experiment that decisively narrows a design space. In each case, novelty is a hypothesis about what the work may reveal, not a result announced ahead of measurements. Until a preregistered comparison demonstrates a useful difference, no superiority claim follows.

The master plan’s guiding rule is therefore modest: own the algorithm where that is the ambition; use a baseline adapter when it is needed for fair comparison; keep the application backend pinned and supported; record the limits of each. Baselines are not surrender, and “we implemented our own” is not a quality certificate. Both can coexist with honest measurement.

## C11 — Capabilities 1–5: compression, serving, scheduling, kernels, recovery

The register’s first group concerns computation and the conditions that let it run.

**1. Sub-4-bit quantization — in progress.** The proposed owner is model optimization, working with Product 43 research and supported application adapters. The registered dependencies are 10, 18, and 20: tokenizer conversion, profiling, and format translation are relevant before the program can fairly claim a useful compressed deployment. The branch implements groupwise low-bit packing and a trained-P43 research evaluation. The program gate requires effective bits including metadata, an explicit quality ceiling, and a separately measured runtime benefit. Its existing milestone is a reference format and diagnostic experiment, not evidence that compression creates speed or model utility.

**2. Serving with dynamic KV cache — in progress.** Runtime engineering, Product 20, and Product 45 are proposed integration owners. Dependencies 9 and 18 mean safety evaluation and profiling are expected at the integration gate. The P43 research decoder maintains incremental per-layer key/value state and checks parity against a full-prefix reference. The full capability still needs a pinned application backend, memory accounting, isolation, cache ownership, eviction, cancellation, overload behavior, and control-plane approvals. A string labelled `owner` in a research runtime is not authentication; a local decoder is not a network model service.

**3. Dynamic batching — in progress.** A runtime scheduler behind the current control plane is proposed, dependent on 2 and 18. The milestone exercises real heterogeneous-length CPU batches and bounded round-robin scheduling in P43. The eventual acceptance question is not “can it combine inputs?” but whether a trace-driven policy improves throughput without violating declared tail-latency, memory, fairness, and cancellation constraints under representative arrivals. A batch that is fast for a short synthetic trace can be slow or unfair for a real mixture.

**4. Sparse CUDA kernels — planned.** Accelerator engineering and profiled operators are the intended owners; capability 18, the profiler, is the listed prerequisite. At the pinned branch checkpoint, the host probe did not find `nvidia-smi`, `nvcc`, or PyTorch, so GPU execution was unmeasured. The acceptance gate calls for explicit useful sparsity, a CPU reference, hardware support matrix, and end-to-end benefit over tuned dense baselines. Sparse operations can lose to dense ones when memory movement and indexing dominate. No kernel, no speedup, and no GPU benchmark should be conjured from an architectural wish.

**5. Distributed checkpoint storage — in progress.** Artifact infrastructure is the proposed owner; its register dependency is 14, data versioning and lineage. The branch’s original checkpoint bundle stages content-addressed shards and makes the manifest the commit point. Its P43 adapter separately checks model, Adam optimizer, and PCG64 random-state artifacts, then demonstrates exact continuation on a constructed 719-parameter fixture. This is strong local evidence for the supported path. It is not a distributed storage service. The full gate still requires multi-client coordination, authorized remote storage, large checkpoints, interruption and recovery tests, and a matched throughput baseline.

Those distinctions are especially important because “distributed checkpoint storage” sounds like a property of the manifest. A manifest can identify a set of bytes. It cannot provide network consensus, availability, access-control identity, or crash consistency that the underlying store does not have. The original bundle is a meaningful first primitive; the unearned suffix is “distributed.”

## C12 — Capabilities 6–10: memory, retrieval, assurance, tokenizer, translation

**6. Reflective-memory agent — planned.** Agent engineering with Products 01, 20, and 44 is proposed; dependencies 9 and 14 place evaluation and lineage beneath the integration gate. The intended memory should preserve scoped observations, hypotheses, decisions, source evidence, correction paths, expiry, and restart replay. The important non-goal is quiet rewriting of trusted knowledge. Reflection that cannot distinguish a remembered hypothesis from a verified fact is not learning with accountability; it is a filing cabinet with a confidence problem.

**7. Vector indexing — in progress.** Retrieval engineering with Product 20 and corpus consumers is the proposed owner; capability 14 is the listed dependency. The branch implements exact cosine/L2 search, pinned manifests, deterministic ties, immutable generations, and a source-hash-verified lexical adapter around actual RAG chunks. It establishes a useful exact reference and stale-source rejection. It does not provide a learned encoder, approximate-nearest-neighbor comparison, relevance labels, deletion lifecycle, or semantic answer quality. “Vector index” is not a synonym for “understands the corpus.”

**8. Self-healing RAG — in progress.** Retrieval engineering with Product 20, the bot, and Product 44 owns the proposed stage; dependencies are 7 and 9. The plan calls for failure classification and bounded repair while retaining citations, negative-query behavior, and the same authority boundaries. A repair that silently substitutes a nearby document can make a result look healthier while making it less trustworthy. The acceptance path needs to show what was stale, what was rebuilt, what was rolled back, and whether the revised citation actually supports the answer.

**9. Safety and alignment evaluation — planned.** The assurance owner would work with Products 20, 22, and 26. The register has no dependencies for starting this work, but the eventual test suite is a prerequisite for several downstream capabilities. The program asks for frozen, task-specific benign/adversarial tests measuring utility, abstention, attack success, and escalation. It explicitly refuses a universal “alignment” certificate. A model can pass one suite and fail an adjacent task; a result needs its scenario, model identity, prompt, retrieved content, and threshold.

**10. Lossless tokenizer converter — in progress.** Model interoperability owns the proposed adapter. The branch implementation supports a narrow Unicode-scalar character representation and actual P43 metadata layouts while preserving token-ID order and identity normalization. Unsupported BPE/SentencePiece semantics, added or special tokens, unknown replacement, and altered normalization are rejected rather than waved through. That is the correct engineering posture: “lossless for this declared equivalence class” is meaningful; “universally lossless” is not. Capability 10’s in-progress status does not mean all tokenizers can be made interchangeable.

Together these capabilities expose a valuable sequencing principle. A source-bound exact retrieval baseline should precede an approximate index; an immutable tokenizer contract should precede model format translation; a safety suite should exist before a repair mechanism is trusted to change what an assistant sees. Dependencies protect validation claims, not curiosity. Teams can explore a stage early, but they must not present that exploration as if the integrated dependency had already been satisfied.

## C13 — Capabilities 11–15: temporal data, synthetic data, drift, lineage, defense

**11. Serverless real-time feature store — in progress.** Data engineering with Products 21 and 40 is proposed, but the plan rightly asks for actual model consumers before a feature store is built around an empty slot. The register dependency is 14. The branch connects the Product 40 transport to availability-aware snapshots and a source-linked DAG through local CLI/API interfaces. Its USGS attempt failed DNS before receiving response bytes; no archive was created and no synthetic substitute was supplied. Thus the local temporal foundation exists, but there is no verified live ingestion, retained raw-payload replay, predictive consumer, or serverless service qualification.

**12. Domain synthetic data — planned.** Data/model engineering with Product 03 EIGE is the proposed start; dependencies 9 and 14. The first deliverables are seeded generators, ancestry, split isolation, downstream utility on untouched real holdouts, and applicable privacy assessment. Synthetic rows can make controlled experiments possible. They can also reproduce their generator’s blind spots or leak entities across splits. Their artificial origin should travel with the data, not be mentioned once in a README and then lost.

**13. Prediction drift monitoring — in progress.** Monitoring with Products 21 and 40 is proposed, dependent on 11. The branch implements a tied empirical Kolmogorov–Smirnov statistic and a conservative two-sample union-DKW bound, plus seeded stationary/shift replay. The code separates distribution-drift observations from model-performance drift. Without labeled outcomes, it cannot say whether predictive quality worsened; without repeated-monitoring error controls, one bound does not establish a safe alert policy. Real prediction streams and outcome delays remain prerequisites for the stronger claim.

**14. Data versioning and feature lineage — in progress.** Data and artifact infrastructure is the proposed owner; it has no listed dependency. The branch implements a content-addressed, closed lineage DAG with source, temporal snapshot, feature, derived artifact, model, and index kinds. It checks allowed parent kinds and explicit owner/origin assertions and can describe an advisory deletion closure. The word “advisory” matters. A manifest does not prove a source’s authenticity, a caller’s rights, execution, actual storage deletion, or model unlearning. Those are different properties with different evidence.

**15. Adversarial defenses — planned.** Assurance/security integration with Product 22 and Product 20 is proposed, depending on 9. The acceptance plan calls for threat-scoped prevention and detection, including poisoned retrieval and cross-owner access. It refuses an “attack-proof” label. A useful defense test says what the attacker can control, which component is exposed, what the success criterion is, and what behaviors remain out of scope. A handful of safe refusals is not a universal warranty.

This group is where provenance and authority meet. A live feature is not merely a value; it has event time, availability time, source status, ownership, and correction history. A synthetic value is not a live fact. A model index derived from a source should keep lineage. A deletion request should propagate through every known derivative, while the implementation remains honest about backups and already-trained models. A drift alert should say whether it detected a changed input distribution or changed outcomes. These details are not paperwork around intelligence. They determine which question the system is actually answering.

## C14 — Capabilities 16–21: fairness, explanations, profiling, learning, formats, modalities

**16. Fairness audit — planned.** Assurance with a domain steward is the proposed owner; capability 9 is its listed prerequisite. An audit needs defined decisions and harms, lawful group data, intersectional sample sizes, uncertainty, unknown membership, and thresholds approved for the domain. Underpowered results should be withheld, not rounded into a universal badge. Fairness is not a number that can be detached from a decision and its affected population.

**17. GPU explainability — planned.** Model interpretability/accelerator owners would start from faithful CPU/reference explanations, then assess GPU parity; dependencies 9 and 18 are listed. The plan calls for perturbation and randomization checks before measuring acceleration. An attractive visualization is not an explanation if it fails to track the model’s actual behavior. A GPU path that is fast but differs from the reference must not inherit the reference’s interpretation without checking equivalence.

**18. Hardware profiler — in progress.** Runtime observability with Product 01 and Product 45 is proposed; it has no listed dependency. The branch’s CPU profile collects warmed wall and process-CPU samples, nearest-rank percentiles, Python allocation peaks, and hardware observations. It profiles declared workloads, including quantization; it does not measure native memory, GPU utilization, hardware counters, or application serving latency. Profiler overhead and a shared host also matter. The remaining work is to connect representative pinned workloads, native or GPU measurement, contention observations, and bottleneck attribution.

**19. Modular reinforcement learning — planned.** Agent research with Product 20 test environments is proposed, dependent on 6 and 9. Before production learning, the environment needs versioned observations, actions, rewards, deterministic replay, seed variance, a baseline, termination rules, and operator override. Learning against a badly specified reward can optimize the wrong thing very efficiently. Production adaptation remains a separate and more consequential stage.

**20. Model format translation — in progress.** Model interoperability with Products 43 and 45 is proposed, depending on 10. The branch supports bounded P43 inference NPZ-to-AZMQ conversion with explicit lossy opt-in and reverse reconstruction of the already reconstructed weights. It distinguishes serialization, quantization, optimization, and distillation instead of calling every conversion an optimization. Quantization discards information; the reverse path cannot restore the original weights. A supported pair is a real milestone, not universal ONNX/GGUF equivalence or measured runtime improvement.

**21. Multimodal vector database — planned.** Data/retrieval work with Product 41 extraction and Product 20 consumers is proposed, dependent on 7 and 14. A shared lifecycle would still need modality-specific encoders, aligned retrieval benchmarks, access and deletion controls, and safe generation rebuilds. Images, audio, text, and video cannot be made semantically interchangeable by placing their vectors in one table. A shared asset identity and lifecycle can unify operations while the encoders and evaluations remain modality-specific.

The six capabilities are not six checkboxes that can be solved by adding one database and one GPU. They are research questions and engineering obligations with distinct definitions. Fairness requires a domain’s concepts of harm; interpretability requires fidelity; profiling requires hardware and workload observability; RL needs a controllable environment and safe operator boundary; format translation needs explicit semantic compatibility; multimodal retrieval needs evaluation across modalities. The plan correctly leaves some in “planned” status rather than inventing premature implementations.

## C15 — Results that have been measured, results that have not

The branch’s strongest contribution is not that it declares all twenty-one capabilities complete. It says the opposite. It implements original CPU reference components and records several unflattering results alongside successful narrow gates. This is how an ambitious plan becomes more credible: it narrows claims when the evidence narrows them.

### The native model-quality results

The program looked for an existing tracked trained checkpoint. It found none among the checked formats: NPZ, NPY, safetensors, PT/PTH, or GGUF. The branch therefore selected an explicitly labeled local research baseline using Product 43 and constructed arithmetic data. It did not download an application model and did not relabel a deterministic responder as inference.

The first native arithmetic baseline was fixed to 60 training, 10 validation, and 30 test operand pairs. The held-out test remained out of training and quantizer fitting. The recorded native model answered **0/30** arithmetic questions correctly. Its teacher-forced token accuracy, 58.67%, included format and punctuation and was not a substitute for answer accuracy. The native cross-entropy was 2.121831 nats. The original 3-bit artifact answered 1/30 and failed the relative fidelity limit; its complete representation was 3.396636 bits per parameter, while cross-entropy rose to 2.887404 nats. The 4-bit variant occupied 4.397933 bits per parameter, passed the declared relative fidelity criterion, and still answered 0/30. Preserving token behavior relative to an inadequate baseline did not make the model useful.

The requested target was then made explicit: 30/30 on a fresh preregistered holdout, keeping the original test diagnostic only. The first answer-only attempt used actual P43 neural inference, validation-selected checkpointing, and 30 withheld unit-pair computations. It completed training and passed its validation examples, but **failed the same fresh target at 0/30**. The diagnosis showed that validation reused the 70 underlying unit-pair computations found in training, though in new two-digit strings. That is an evaluation-design weakness, not a reason to erase the failure or recast the result as successful generalization.

A second, separate modulo-11 task explicitly separated underlying computation/reversal classes across the 81/10/30 splits. It was not a disguised repair of the modulo-10 benchmark. It achieved 81/81 on training, 0/10 validation, and **0/30 on the fresh test**. The validation failure appeared before test evaluation; no test-selected retry or relaxed threshold was used. This is the second 0/30 native learned attempt on a separate answer set. Both outcomes remain recorded. No 30/30 has been achieved, and the program says so.

The branch also investigated implementation defects without claiming that every possible cause had been ruled out. A separate NumPy forward/reverse implementation compared logits, loss, all parameters’ gradients, Adam moments, and successive updates against P43 on constructed cases; it passed those parity checks within the fixed tolerance. Sampled finite differences passed their stated criterion on the selected training-only rows. An attempt to install PyTorch for an external-framework comparison failed package-host DNS; therefore no such comparison exists. These checks reduce one class of implementation-bug hypothesis. They do not prove generalization, training quality, or a cause for the failures.

### Calibration is not utility

A later, validation-only calibration search evaluated six group sizes and selected a 3-bit artifact of **3.441427 complete bits per parameter**, including framing and metadata. It met the unchanged relative fidelity thresholds on validation and, only after selection, passed a diagnostic on the already exposed original test (cross-entropy delta +0.2231491 nats and token-accuracy delta −0.0866667). The packed model still answered 1/30; the native model remained at 0/30. That result is a bounded compression-fidelity observation on a known inadequate model. It is not fresh quality qualification, a fix to the 30/30 gate, or evidence of better arithmetic.

Likewise, an independent reference benchmark contains synthetic numerical weights, three orthogonal retrieval axes, and seeded Gaussian drift replay. Those fixtures can check a declared implementation and threshold. The two repository-RAG fixtures search actual documents and verify source paths, but the README says they are lexical examples, not a semantic-quality benchmark. A fixture can be rigorous and still be a fixture. We should neither dismiss it nor inflate it.

### The hosted safety case

The recorded hosted Windows CPU candidate evaluation used pinned Qwen3-1.7B Q4_K_M and passed **3 of 4** sanity cases. The retrieval-injection case did refuse the malicious request and retained unsupported-platform limits. It failed because its explanation described only those limits and did not identify the retrieved instruction as malicious, unsafe, or untrusted. That expected rationale was unchanged. Authentication checks returned 401 for missing or incorrect keys; the server stopped; model output was not executed. The board explicitly characterizes this as a real safety/quality shortfall, not a harness failure and not production qualification.

The distinction deserves precision. The candidate performed a protective refusal, yet did not communicate the trust boundary the evaluator required. The recorded case is therefore a partial success in one behavioral dimension and a failure on its predeclared acceptance test. We must not round 3/4 to “safe,” change the rationale after observing the answer, or equate authentication checks with model alignment. Nor should we generalize from one test case to declare the entire PC Suite unsafe. It is an exact, pinned candidate result that remains unresolved.

### The feed and the checkpoint

The program’s retry against the USGS feed failed DNS with `Errno -5` before response bytes. No raw archive was created and no synthetic or cached fallback was substituted. That is not live-ingestion success. It is a useful honesty test: the failure remains an error rather than being covered by a plausible-looking record.

The checkpoint work also has a specific boundary. The generic bundle uses content-addressed shard bytes and a manifest commit point; a constructed local fixture tested interruption before manifest publication, recovery, checksum rejection, and wrong-scope rejection. The P43 adapter then restored model, Adam, and PCG64 state and matched the next update exactly on a 719-parameter fixture. The board reports that a writer process ended immediately after the durable local commit, then a fresh interpreter restored and fingerprinted state. This is **process restart on one local filesystem**. It is not evidence of recovery from power loss, a mid-commit crash, distributed workers, network storage, a production service, or hardware-level crash consistency. `fsync` and a successful fresh process are not a distributed storage system.

### What a green regression does and does not say

The branch board records an unfiltered core command, `python -m pytest tests/ -m "" -q`, completing with 62,077 passed, 71 skipped, zero failed, and zero deselected for that checkpoint. That is a repository regression result as recorded by the branch. It does not mean I ran that command in the present writing session. The branch’s own program tests also check register and bookkeeping behavior; a register test cannot certify the model quality, safety of all tasks, completeness of the feature store, or external deployment readiness. Passing tests are useful evidence at their scope. No test count should be used as a substitute for the result of a different experiment.

## C16 — Integration gates, owners, and a humane sequence

The master plan gives all twenty-one workstreams a home in the existing product landscape. The owners are engineering roles, not named staffing commitments. Before a package starts, it should have a bounded objective, prerequisites, file ownership, acceptance command, stop condition, and handoff. A distinct reviewer should challenge the implementer; a human domain steward should own consequential decisions. Several assistants that share assumptions are not independent confirmation.

The sequence begins with **truth, contracts, and a baseline**: inspect real source; freeze workload identities and non-claims; establish held-out evaluation and resource accounting; and change the execution spine only where a contract requires it. This prevents a performance story from arriving before a reproducible baseline, and it helps ensure that source identifiers, licenses, and data origins travel with artifacts.

From that base, the plan proposes two independently promotable vertical slices. The first is a governed evidence assistant: one pinned model, tokenizer, backend, permitted corpus, scoped retrieval/memory, and one bounded approved tool operation. Its tests must include relevant and negative queries, supported citations, restart, refusal, failure, and unavailable-backend behavior. Citation existence is not entailment. A configured endpoint is not proof that full inference works. The second slice is temporal data replay: a P21/P40 source, availability-aware transforms, and a clearly identified predictive consumer. It must handle late corrections and data quality; live-feed connection is a separate step, and performance drift requires outcomes.

After those slices, runtime work proceeds from measured baseline to persistent serving, KV accounting and isolation, then continuous batching. Retrieval proceeds from source manifest and encoder to exact search, approximate comparison, bounded repair, and multimodal expansion. Original quantization, scheduling, indexing, the toroidal architecture, and synthetic generation are compared with named conventional baselines under matched workload and held-out data. The plan does not require inventing a CUDA kernel before useful serving exists. Conversely, it does not allow an early-stage experiment to inherit the acceptance status of its downstream capability.

Scale and deployment come last where prerequisites warrant them: distributed storage, serverless services, GPU explainability, multimodal stores, and RL training. Their graduation gates include recovery, rollout and rollback, retention and deletion, compatibility, security review, operational ownership, and evidence on representative workloads. Calendar and budget should be set after hardware and staffing are known, not to make a plan look complete.

The shared contracts are deliberately richer than a filename. A model identity includes weights, architecture, tokenizer, precision, backend, license, and evaluation identity. An asset includes owner and scope, rights and purpose, schema and units, event and availability time, origin, parent assets, and deletion state. A transform/run binds input and code/environment/config identities to outputs and split policy. An index records corpus snapshot, encoder, tokenizer/chunker/preprocessing, dimension, normalization, metric, access scope, and generation. A feature records entity key, temporal semantics, freshness, missingness, and correction policy. An execution records requester, owner, approval, budget, cancellation, backend, effects, outputs, and failures. An evaluation records immutable identities, scenarios, groups, labels, metrics, uncertainty, thresholds, environment, hardware, and skipped or unsupported status.

Those fields do not guarantee truth. A content hash establishes identity, not authenticity, consent, entailment, or unlearning. Rights and purpose fields need an accountable source. A valid test report is not a license grant. A model can retain information after its index is deleted; retention and the limits of unlearning must be stated. A human’s authorization is not inferred from a public URL.

There is a humane reason to state these boundaries clearly. A scientist should not have to guess whether an error means “not observed” or “probably fine.” An operator should not have to infer whether a button submits a real action or opens a local preview. A subject should not have to discover after a data migration that deletion did not reach derived indexes. An evaluator should not be asked to accept a model because a dozen related tools reported success. Honest unavailable states are a service to the next person in the chain.

### The next useful result

The branch’s current handoff points toward a measured next step rather than a celebratory launch. First, diagnose the task-generalization failure using training/validation only, with the independent training reference and a new preregistration before another untouched holdout. Keep all exposed failures frozen. Second, evaluate the selected quantizer on a useful model, compare an independent quantizer and licensed application backend, then connect serving through existing approvals. Third, add retrieval rebuild proposals and human-governed rollback with a learned encoder and scoped reflective-memory replay. Fourth, retry a real feed only on a network-enabled host under explicit retention and connect a named model consumer before calling it a feature service. Fifth, test checkpoint integration with actual training state and authorized multi-worker/storage failure experiments. The remaining planned capabilities—safety, synthetic data, fairness, GPU, RL, and multimodal indexing—stay in scope.

This is not a claim that the program has achieved novel capability. It is a plan for testing whether an original algorithm or integrated system earns that description. A toroidal positional mechanism might prove useful; the small current tests do not establish it. A more coherent evidence graph could reduce source drift; a retrieval benchmark must measure that. A profile could reveal a bottleneck; representative hardware must confirm it. A multi-product workflow could produce a result no component alone exposes; the preregistered experiment must show that result and its uncertainty. If it does not, the negative outcome still has value: it prevents investment from being mistaken for evidence.

That is the distinction between an ambitious program and an ambitious claim. The first can retain all twenty-one goals, revise its order, and learn from failure. The second tends to treat each proposed capability as already earned. The register in this branch chooses the first path. It records twelve in progress, nine planned, and none complete. I will not improve that number with prose.

The work is also bounded by the larger PsiCat ecosystem integration plan. Product 20 remains the control plane; Product 44 composes existing strands but does not replace their owners; Product 26 accounts for evidence without certifying truth; Product 42 discovers capability but does not grant authority; Product 45 presents an offline portfolio without implying universal installation. Context-parity, browser roundtrip, migration, orchestration, geometry, and kernel work remain staged rather than assumed. The execution spine remains canonical. The human steward retains scope, consent, risk, publication, and release decisions.

At the end, the question is not whether the braid looks elegant in a diagram. It is whether each strand can be identified, tested, corrected, and stopped when its prerequisites fail. A program that can do that may eventually produce results worth celebrating. It has not yet been asked to pretend.
